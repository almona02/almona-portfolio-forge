## Domain model: “Project”, “Position/Pose”, and “Job”

In code, the central object is `WindowUnit` (`src/types/fabricator.ts`). It’s used as:

- **Position/Pose**: a single opening (e.g., POS-12) with width/height/grid/components.
- **Job**: `useJobsStore` names the list `jobs: WindowUnit[]`.
- **Project** (header): represented separately in DB as `fabricator_projects`, but UI often groups positions by `projectCode || orderNumber`.

Key fields on `WindowUnit`:
- **Identity**: `id`, `orderNumber`, `posNumber`
- **Design state**: `grid?: WindowGrid`, `components: WindowComponent[]`
- **Production state**: `optimization: OptimizationResult | null`, `status`
- **Grouping**: `projectCode?`, `customer?`, `systemPackId?`, `quantity?`
- **Large project metadata**: `positionMeta` (flat/floor/elevation/etc.)

Source: `src/types/fabricator.ts`

## Persistence & state: what actually saves, where, and why

There are **two primary state systems** plus targeted persistence services:

### 1) `useJobsStore` (Zustand) — “positions list” + Supabase sync

File: `src/store/jobsStore.ts`

- **`loadJobs()`**
  - Fetches `fabricator_projects` + `fabricator_positions` for `owner_user_id`
  - Joins positions → project header (via `project_id`)
  - Produces `jobs: WindowUnit[]` (note: `components` are set to `[]` in the “fast list” mapping)

- **`addOrUpdateJob(job)`**
  - Updates local `jobs` array
  - Fire-and-forget background sync:
    - upserts a `fabricator_projects` header keyed by `project_code`
    - upserts a `fabricator_positions` row for the job (by id if valid UUID, else by `(project_id, order_number, pos_number)`)
  - Also includes a stub ERP sync hook (`ConnectivityFactory`), disabled by default.

This store is what powers the “Projects & Positions” UI (`src/pages/Projects.tsx`) and is the most direct “DB ↔ UI list” bridge.

### 2) `FabricatorWorkspaceContext` — “current selection + drafts + constitutional audit”

File: `src/context/FabricatorWorkspaceContext.tsx`

State includes:
- `currentProject: WindowUnit | null`
- `draftQuotes`, `draftInvoices` (commercial workspace drafts)
- `profileEdits`, `inventoryEdits`
- `snapshots`
- `projectDraftStates` + `constitutionalAudit` (pose-level deterministic draft state + audit trail)

Persistence:
- On mount: loads snapshot via `WorkspaceSyncService.loadWorkspaceSnapshot()`
- On every state change: debounced save via `WorkspaceSyncService.saveWorkspaceSnapshotDebounced(state, 3000)`

File: `src/lib/workspace/WorkspaceSyncService.ts`
- Prefers Supabase table `workspace_snapshots` (upsert by `user_id`)
- Falls back to compressed localStorage (key = `fabricator-workspace-v1`)

### 3) `ProjectPersistenceService` — “pose snapshot” persistence (grid/components/etc.)

File: `src/lib/fabricator/ProjectPersistenceService.ts`

Purpose: save/load a **pose snapshot** with grid + selected preset + metadata, with:
- Primary: Supabase `fabricator_projects` + `fabricator_positions`
- Secondary: localStorage (`almona-project-persistence-{poseId}`)

Important implementation details:
- Ensures a `fabricator_projects` row exists to obtain `project_id` UUID for `fabricator_positions`
- Writes a richer `fabricator_positions` payload including `grid`, `components`, `hardware`, `selected_preset`, `project_code`, `customer`, `meta`, plus “alias” columns (`overall_width`, `window_type`) used for compatibility

This is aligned to DB migration `migrations/059_add_fabricator_positions_columns.sql`, which adds those missing/alias columns and a sync trigger.

## Engineering Bay: the design cockpit (SmartDraw + Drafting + 3D + BOM)

### Entry wiring

`EngineeringBay` is a core component used in multiple flows:

- **Workflow/Design Studio**: `EngineeringBayWrapper` (`src/components/fabricator/EngineeringBayWrapper.tsx`)
  - Reads `projectId` param and looks it up in `useJobsStore.jobs` by `id`
  - Otherwise uses `FabricatorWorkspaceContext.state.currentProject`
  - Calls `onDesignComplete` → updates context → navigates to `/fabricator/workflow/design`
  - Note: `profiles` are currently `[]` in wrapper; the engine mainly relies on `SYSTEM_PACKS` for system pack data.

- **Project Studio (full-screen)**: `ProjectStudio` (`src/components/fabricator/project/ProjectStudio.tsx`)
  - Maintains its own local `project.units[]`
  - Passes `profiles` from `SYSTEM_PACKS.flatMap(pack.profiles)`
  - Uses `EngineeringBay` in “expert” mode

### Core engine hook

`EngineeringBay` uses `useEngineeringEngine` (`src/hooks/fabricator/useEngineeringEngine`) to create:
- `liveProject` (derived window unit)
- `currentGrid`
- `activeSystemPackId`
- `bomData`
- `actions` (apply grid, update grid, validate, select system, drafting→smartdraw, etc.)

### SmartDrawCanvas (SVG editor)

File: `src/components/fabricator/SmartDrawCanvas.tsx`

Key capabilities:
- Grid rows/cols, proportional row/col weights
- Cell type cycling (fixed/sash/sliding/panel/empty) + sash opening direction
- Manual mullions (frame-level + sash-level), with explicit mm position input
- Undo/redo history
- Multi-select + copy/paste + mirror
- Optional preset patterns + ML preset suggestions (`presetMatcher`)
- Touch gestures: pinch zoom + 2-finger pan
- Outputs: controlled `WindowGrid` via `onGridChange()`

### DraftingWorkbench (gold-tier drafting mode)

In `EngineeringBay`, drafting mode is a first-class design mode:
- `designMode: 'smartdraw' | 'drafting'`
- `useModeSwitch` ties into constitutional pose sync (`src/hooks/fabricator/usePoseSync`)
- Drafting output is converted to a `WindowGrid` via `convertDraftingToWindowGrid` and then applied back into the engineering engine.

### 3D + physics + BOM

`EngineeringBay` also wires:
- `Window3DGenerator` (lazy)
- `StructuralValidator` + `ThermalEngine` (physics panels)
- `CrossSectionGenerator` (SVG cross-sections)
- `BOMSidebar` (production BOM view)

Source: `src/components/fabricator/EngineeringBay.tsx`

## Optimization & cut lists (Fabricator Pro production truth)

There are two distinct optimization pathways:

### A) Project Studio optimization (ApexEngineV6 per-unit)

File: `src/components/fabricator/project/ProjectStudio.tsx`

- `Optimize All` runs `ApexEngineV6(pack, unit, 'miter').generate()` per unit
- Stores results in `unitResults: Map<unitId, ApexV6Output>`
- Passes to `ProjectOptimizer`

`ProjectOptimizer` (`src/components/fabricator/project/ProjectOptimizer.tsx`):
- Shows per-unit efficiency, waste, bars count
- Exports CSV via `src/lib/fabricator/CutListExport.ts`
- Prints ALMONA style using `printCutListAlmonaStyle()`
- Uses `CutListViewer` but currently passes `frameStock as any` (adapter mismatch is noted inline)

### B) Workflow optimization (position-level `optimization` on `WindowUnit`)

The legacy `FabricatorWorkflow.tsx` and route-based pages use `currentProject.optimization` in `FabricatorWorkspaceContext`.
This is what the commercial engine (below) expects when generating quotes from the “active project”.

## Commercial workspace: quotes/invoices connected to the active Fabricator context

File: `src/pages/CommercialPage.tsx`

Key link:
- When you create a draft quote, it reads `state.currentProject` from `FabricatorWorkspaceContext`.
- If `currentProject.optimization` exists, it calls `new QuotingEngine().generateQuote(project, optimization)`.

`QuotingEngine` (`src/modules/commercial/QuotingEngine.ts`):
- Converts optimization `costBreakdown` into line items (material/labor/hardware/glazing/installation)
- Applies markups (configurable defaults)
- Produces a `Quote` containing “contract-grade” sections (parties, scope, technical summary, payment terms, warranty, general terms)
- Stamps “constitutional” metadata for liability boundaries

Commercial persistence today is **workspace-state-based**:
- Draft quotes/invoices are stored in `FabricatorWorkspaceContext` and persisted through `WorkspaceSyncService` (Supabase `workspace_snapshots` or localStorage fallback).
- The DB `quotes` / `orders` tables exist in `src/types/database.ts`, but this page currently operates on **draft** objects.

## Database wiring (Supabase): what Fabricator actually uses

### Tables & relationships (core Fabricator)

From migrations and runtime queries:

- `fabricator_projects`
  - key fields: `id (uuid)`, `owner_user_id`, `project_code`, `client_name`, `system_pack_id`, `status`, `meta`

- `fabricator_positions`
  - required: `project_id → fabricator_projects.id`, `owner_user_id`
  - canonical dims: `overall_width_mm`, `overall_height_mm`
  - canonical type: `type`
  - plus JSON: `position_meta`, `optimization`
  - plus extended columns added in migration 059: `components`, `grid`, `hardware`, `selected_preset`, `project_code`, `customer`, `meta`, and alias columns (`window_type`, `overall_width`, `overall_height`)

Schema sources:
- `migrations/009_fabricator_projects_and_team.sql`
- `migrations/059_add_fabricator_positions_columns.sql`
- Type mapping: `src/types/database.ts`

### “FabricatorClient” (Supabase wrapper)

File: `src/lib/supabase/fabricatorClient.ts`

This is a robust wrapper providing:
- user isolation (`getUserId()` + `.eq('user_id', userId)` style guards)
- retries, performance metrics, audit logging (`audit_logs`)
- realtime subscriptions for `fabricator_profiles` and `fabricator_accessories`
- mapping helpers for `Profile` and `FabricatorAccessory`

Note: It focuses on **profiles/accessories/compatibility**, while **projects/positions** are mostly handled by `useJobsStore` + `ProjectPersistenceService`.

## Important wiring mismatches / sharp edges (observed from code)

- **“projectId” route param frequently carries a position/job UUID**:
  - `EngineeringBayWrapper` uses `projectId` but looks it up in `jobs.find(job.id === projectId)`.
  - This is effectively a **poseId**.

- **Legacy path usage still appears**:
  - Some code navigates to `/fabricator/workflow/engineering-bay/...` (alias route),
  - but `App.tsx` redirects that to `../design`.
  - This works, but it’s a naming mismatch that can confuse future work (and any URL-based analytics).

- **Project Studio vs JobsStore are currently separate universes**:
  - `/fabricator/studio/project/:projectId` uses `ProjectStudioWrapper` which **mocks** project data and doesn’t load from Supabase/jobs.
  - `/fabricator/projects` is driven by `useJobsStore` and Supabase.
  - If “Studio Project Workspace” is meant to be the Pro path, it needs a binding layer that loads `fabricator_projects` + `fabricator_positions` into the ProjectStudio “units” model.

- **Type/schema drift is intentionally bridged by migration 059**:
  - Code writes `grid/components/hardware` into `fabricator_positions`, but those are not in the original migration 009.
  - Migration 059 exists specifically to reconcile this.

## What to build next (based on the current wiring)

If “Fabricator Pro” is defined as: **Projects (headers) → Positions (poses) → Engineering Bay (design) → Optimization (cut lists) → Commercial (quote) → Production**, then the codebase is already 70% wired, but split across two flows.

Highest-value consolidation path:
- Make `ProjectStudioWrapper` load from Supabase:
  - Load `fabricator_projects` by `projectId` (uuid) and load all `fabricator_positions` for that project.
  - Adapt positions to `ProjectStudio`’s `units: WindowUnit[]`.
- Standardize route params:
  - Rename param to `:poseId` where it is a position id, or thread both `:projectId/:poseId`.
- Choose one persistence authority:
  - either `ProjectPersistenceService` for pose snapshots + `useJobsStore` for lists,
  - or a unified “ProjectsService” that wraps both and provides cached queries via React Query.
