# BOM Elements Integration Analysis

## Overview
Analysis of how BOM (Bill of Materials) elements integrate in the 3D window geometry system (`src/lib/3d/windowGeometry.ts`).

**Date:** January 2026  
**Status:** ✅ **VERIFIED & DOCUMENTED**

---

## BOM Elements Structure

### 1. Frame ✅ **INTEGRATED**

**Location in Geometry:**
- `FrameGeometry.frame: { profile: ProfileCrossSection; parts: MiteredFrameData[] }`

**Implementation:**
- 4 mitered frame parts (top, bottom, left, right bars)
- Generated by `createMiteredFrame(width, height, profile)`
- Uses `ProfileCrossSection` from `WindowUnit.components[0].profile`
- Frame parts use `MiteredFrameData` with transformation matrices

**Data Flow:**
```
WindowUnit.components[0].profile 
  → generateProfileCrossSection(profile)
    → createMiteredFrame(width, height, frameProfile)
      → FrameGeometry.frame.parts (4 MiteredFrameData objects)
```

**Status:** ✅ **FULLY INTEGRATED**

---

### 2. Sash ✅ **INTEGRATED**

**Location in Geometry:**
- `FrameGeometry.sashes: SashData[]`

**Implementation:**
- Each sash is a `SashData` object containing:
  - `parts: MiteredFrameData[]` - Sash frame (4 parts, similar to main frame)
  - `glass: BufferGeometry[]` - Glass panes inside sash
  - `spacers: BufferGeometry[]` - Glass spacers (IGU - Insulated Glass Unit)
  - `openingPath: { position: Vector3; rotation: Euler }` - For animation

**Data Flow:**
```
WindowUnit.grid.cells (type === 'sash')
  → createMiteredFrame(sashW, sashH, sashProfile) [sash frame]
  → calculateGlassBounds() [glass dimensions]
  → new BoxGeometry() [glass geometry]
  → SashData { parts, glass, spacers, openingPath }
    → FrameGeometry.sashes[]
```

**Status:** ✅ **FULLY INTEGRATED**

---

### 3. Glazing ✅ **INTEGRATED**

**Location in Geometry:**
- `FrameGeometry.fixedGlass: BufferGeometry[]` - Fixed glass panels
- `FrameGeometry.sashes[].glass: BufferGeometry[]` - Sash glass panes

**Implementation:**
- Glass dimensions calculated using `calculateGlassBounds()` function
- Accounts for:
  - Frame profile width (inset)
  - Transom adjustments (if present)
  - Glass inset (default 2mm)
- Glass thickness: 0.006m (6mm) standard
- Glass positioned at calculated bounds, recessed by 6mm

**Data Flow:**
```
WindowUnit.grid.cells + WindowUnit.presetData.transoms
  → calculateGlassBounds(cell, cellX, cellY, cellW, cellH, windowUnit, profile, inset)
    → { x, y, width, height }
      → new BoxGeometry(width, height, 0.006)
        → FrameGeometry.fixedGlass[] OR FrameGeometry.sashes[].glass[]
```

**Status:** ✅ **FULLY INTEGRATED**

---

### 4. Glazing Bead ⚠️ **NOT IN 3D GEOMETRY, BUT IN BOM**

**Location in BOM:**
- `WindowComponent[]` with `type: 'glazing_bead'`
- Generated by `generateGlazingBeads()` in `src/algorithms/utils/glazingBeadUtils.ts`

**Implementation:**
- 4 pieces per cell (top, bottom, left, right)
- Generated during component generation (`generateComponentsFromGrid`)
- Each bead is a `WindowComponent` with:
  - `type: 'glazing_bead'`
  - `profile: Profile` (bead profile)
  - `cuttingLengths: number[]` (glass dimensions)
  - `angles: [45, 45]` (mitered corners)

**Data Flow:**
```
WindowUnit.grid.cells + beadProfile
  → generateGlazingBeads({ cellId, beadProfile, glassWidth, glassHeight, glazingType })
    → WindowComponent[] (4 components: top, bottom, left, right)
      → WindowUnit.components[] (BOM only, not 3D geometry)
```

**Status:** ⚠️ **BOM ONLY - NOT VISUALIZED IN 3D**
- Beads are calculated for BOM/cutting lists
- **NOT represented in `FrameGeometry`** (no `beads` field)
- This is acceptable for visualization (beads are small, internal components)
- But may be needed for production-accurate visualization

---

### 5. Mechanism/Hardware ⚠️ **PARTIALLY INTEGRATED**

**Location:**
- `WindowUnit.hardware: any[]` - Hardware array (not directly used in geometry)
- `WindowComponent.hardware: any[]` - Component-level hardware (not directly used)
- `FrameGeometry.fixedSpacers` - Mechanism geometries added here (via `addOpeningMechanisms`)

**Implementation:**

#### A. Opening Mechanisms (Feature-Flagged) ✅
- Function: `addOpeningMechanisms(windowUnit, pattern)`
- Adds mechanism geometry to `fixedSpacers`:
  - **Tracks**: Sliding track geometry (bottom/top/both)
  - **Hinges**: Casement hinge geometry (3 hinges per sash)
  - **Pivots**: Tilt-turn pivot geometry
  - **Indicators**: Visual indicators (arrows, etc.)
- **Feature Flag**: `ENABLE_OPENING_MECHANISMS` (must be enabled)
- Only works if `pattern.openingMechanism` is specified

**Data Flow:**
```
WindowUnit + pattern.openingMechanism
  → addOpeningMechanisms(windowUnit, pattern)
    → OpeningMechanismGeometry { tracks?, hinges?, pivots?, indicators? }
      → FrameGeometry.fixedSpacers[] (added to existing spacers)
```

#### B. Hardware from WindowUnit.hardware ❌
- `WindowUnit.hardware: any[]` field exists but is **NOT directly integrated** into geometry generation
- Hardware is used in BOM calculations (`HardwareBOMCalculator`)
- Hardware is used in validation (`InterferenceEngine`)
- **BUT hardware is NOT added to 3D geometry automatically**

**Status:** ⚠️ **PARTIALLY INTEGRATED**
- Opening mechanisms are integrated (if feature-flagged and pattern-specified)
- Hardware from `WindowUnit.hardware` is **NOT** automatically visualized
- HardwareSelector component exists but hardware selection doesn't automatically update geometry

## Integration Gaps & Recommendations

### Gap 1: Glazing Beads Not Visualized
**Current State:**
- Beads are calculated for BOM/cutting lists
- Not represented in 3D geometry

**Recommendation:**
- **Option A (Low Priority)**: Add optional bead visualization for production-accurate previews
- **Option B (Recommended)**: Keep as-is (beads are internal, small components; visualization adds complexity)

### Gap 2: Hardware Not Auto-Integrated
**Current State:**
- `WindowUnit.hardware` array exists but hardware is not automatically added to geometry
- HardwareSelector component exists but hardware selection doesn't update geometry
- Opening mechanisms only work if pattern has `openingMechanism` spec

**Recommendation:**
- **Enhancement**: Integrate hardware from `WindowUnit.hardware` into geometry generation
- **Approach**: 
  - Iterate through `WindowUnit.hardware` array
  - For each hardware item, generate geometry based on type (hinge, handle, lock, roller)
  - Add hardware geometry to `FrameGeometry.fixedSpacers` or new `FrameGeometry.hardware` array
  - Use hardware dimensions from `EgyptianHardware` database

### Gap 3: Mechanism Hardware Disconnect
**Current State:**
- Opening mechanisms (tracks, hinges) are added via pattern specification
- Hardware from `WindowUnit.hardware` is separate and not connected

**Recommendation:**
- **Unification**: Map `WindowUnit.hardware` items to opening mechanism geometries
- **Approach**:
  - When hardware type matches opening mechanism (e.g., `hinge` → casement hinges), use hardware positions/specifications
  - When hardware type is standalone (e.g., `handle`, `lock`), add as separate hardware geometry

## Recommendations for Full Integration

### Priority 1: Hardware Integration (High Priority)
**Action:** Integrate hardware from `WindowUnit.hardware` into 3D geometry

**Implementation Plan:**
1. Create `addHardwareToGeometry()` function similar to `addOpeningMechanisms()`
2. Iterate through `WindowUnit.hardware` array
3. For each hardware item:
   - Lookup hardware spec from `EGYPTIAN_HARDWARE_DB`
   - Generate geometry based on hardware type and dimensions
   - Position hardware at specified coordinates
4. Add hardware geometry to `FrameGeometry` (new field: `hardware?: BufferGeometry[]` or add to `fixedSpacers`)

**Files to Modify:**
- `src/lib/3d/windowGeometry.ts` - Add hardware integration function
- `src/lib/3d/windowGeometry.ts` - Update `FrameGeometry` interface (optional: add `hardware` field)

### Priority 2: HardwareSelector Integration (Medium Priority)
**Action:** Wire HardwareSelector component to update `WindowUnit.hardware` array

**Implementation Plan:**
1. When hardware is selected in HardwareSelector, update `WindowUnit.hardware` array
2. Trigger geometry regeneration when hardware changes
3. Ensure hardware positions are calculated correctly (relative to frame/sash)

**Files to Modify:**
- `src/components/fabricator/drafting/components/HardwareSelector.tsx` - Add integration callback
- `src/components/fabricator/drafting/DraftingWorkbench.tsx` - Wire hardware selection to WindowUnit
- `src/components/fabricator/drafting/DraftingCanvas2D.tsx` - Update hardware placement logic

### Priority 3: Glazing Bead Visualization (Low Priority - Optional)
**Action:** Add optional glazing bead visualization for production-accurate previews

**Implementation Plan:**
1. Add `beads?: BufferGeometry[]` to `FrameGeometry` interface (optional)
2. Generate bead geometry in `generateGenericGeometries()` or `generatePresetAwareGeometries()`
3. Only render if feature flag enabled (e.g., `ENABLE_BEAD_VISUALIZATION`)

**Current Integration Status:**
- ✅ **Frame, Sash, Glazing, Spacers, Mullions/Transoms**: Fully integrated
